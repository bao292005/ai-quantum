# Story 4.1 — LUNA Calibration Findings (De-risk Spike) `[RESEARCH]`

Date: 2026-08-06 · Status: **BLOCKED — Success Signal not achievable with v1 features**

## Goal

Before building the calibration mapping + multiprocessing + alert stack, de-risk
the core hypothesis (user-approved): does the MPS fragility (`engine/mps/naive.py`)
actually rise before the LUNA liquidation cascade, giving `RED ≥ 10 min` early with
`< 5%` false positives on the normal control? (Story 4.1 AC.)

Ground truth (`research/ground_truth_labeling.md`): LUNA `cascade_start` = block
14,732,113 (2022-05-07T21:14:48Z), `red_deadline` = 10 min earlier.

## Method

Real code path, no shortcuts: `iter_csv_events` (fixture) → sliding block window
(300 blocks ≈ 1 h, stride 100 ≈ 20 min) → `build_graph` → `adjacency_tensor` +
`feature_tensor` → **minmax `normalize`** → `fragility_raw`. Run on all three
fixtures (LUNA, FTX, normal).

## Findings

### 1. The scoring pipeline was never normalizing features (bug) — and must use minmax

Running `fragility_raw` on the raw `feature_tensor` output gives **`F_raw ≈ 0`
everywhere** (flat, no signal). Cause: `feature_tensor` emits **unnormalized
token-native volume** (~1e18 wei); one hub node (WETH/USDC) dominates the node
mass `m = X·w`, making the coupling matrix effectively rank-1 → entropy ≈ 0.

The 3R.1 spec assumes "X is already normalized (2B.3)", but nothing in the
pipeline applied it. Applying `normalize(X, "minmax")` restores variation.
**`zscore` is invalid here** — it produces negative values, and the node-mass
model requires `m ≥ 0` (`fragility_raw` raises). → the model constrains
normalization to **minmax / non-negative**.

### 2. Even with minmax, there is NO discrimination between crisis and calm

`F_raw` distribution per fixture (157 / 247 / 47 windows):

| Fixture | min | p50 | mean | max |
|---|---:|---:|---:|---:|
| LUNA (crisis) | 0.220 | 0.256 | 0.269 | 0.493 |
| FTX (crisis) | 0.245 | 0.284 | 0.317 | 0.592 |
| **NORMAL (calm control)** | 0.263 | 0.316 | **0.337** | 0.526 |

- **The calm control has the HIGHEST mean fragility (0.337)** — higher than LUNA
  (0.269). The signal is not just weak, it is **inverted**.
- **0 of 157** LUNA windows exceed the normal fixture's max (0.526).
- LUNA's `F_raw` does **not** rise into the cascade: the pre-deadline mean (0.294)
  is *higher* than the post-cascade mean (0.245); the peak (0.493) sits ~18 h
  before the cascade, coinciding with a routine isolated liquidation, not the
  cascade onset.

**Consequence:** no threshold separates crisis from calm. Any RED threshold that
fires on LUNA fires *more* on the normal control → false-positive rate would
exceed the 5% budget. Sigmoid calibration (α, β) cannot fix a missing/inverted
separation. **Story 4.1 AC is not achievable with the v1 feature set.**

## Root cause

The v1 node features are `[tvl_usd, volume_24h_usd, price_usd, volatility,
connectivity]`, but **`tvl_usd`, `price_usd`, `volatility` are hard-zeroed** (2R.1
v1 proxy — deferred as needing reserve-state reads). So the model sees only graph
topology + trade volume. A liquidation cascade is fundamentally a **price /
volatility** event; with those channels zeroed, the input contains no crisis
signal. What remains (volume-share entanglement) is, if anything, *higher* in a
busy-but-calm market.

## Recommendation (decision needed)

**Un-defer the price & volatility features — they do NOT need reserve-state reads.**
Contrary to the 2R.1 assumption, both are computable from schema-0.1 data already
in the fixtures:

- **`price_usd`** — from Uniswap V3 swap `amount0/amount1` ratio (decimal-adjusted)
  on the USDC/WETH pool (15,825 swaps in the LUNA fixture).
- **`volatility`** — rolling std of log-returns of that price over the window.
- (`tvl_usd` genuinely needs reserve state — keep deferred for now.)

This is a real scope change to 2R.1 / 2B.2 (feature sourcing), gated behind this
finding. Only after price/volatility carry signal should we re-attempt 4.1
calibration, then proceed to 4.2 (FTX cross-val), 4.3/4.4 (isolation).

**Also fix regardless:** the scoring path must apply `normalize(X, "minmax")`
before `fragility_raw` (wire 2B.3 into the forward pass; document minmax/non-neg
constraint in 3R.1).

## Follow-up probes (2026-08-06) — which stress feature actually carries the signal?

Direct measurement per window across all three fixtures redirected the fix:

1. **Swap-price volatility (USDC/WETH pool) does NOT discriminate LUNA.** Window
   log-return volatility: LUNA mean 0.0008 / NORMAL mean 0.0008 / FTX mean 0.0014.
   The whitelisted pool is a blue-chip pair that stayed stable through the LUNA/UST
   collapse — the fixture doesn't even contain UST/LUNA tokens (cf.
   `references/luna_comparison.md`). So **price/volatility from the monitored pool
   cannot rescue LUNA detection.** (This revises the §Recommendation above.)

2. **Liquidation rate discriminates but is the label and is coincident, not
   leading.** LUNA max 59/window (mean 4.2) vs NORMAL max 1 (mean 0.06), but it
   only jumps *at* `cascade_start` (0–2 → 4 → 10 → 28), giving no 10-min lead — and
   ground truth defines the cascade *by* this rate, so using it as a feature leaks
   the label.

3. **Aave borrow / utilization rate discriminates AND leads.** Borrow events per
   window: LUNA mean **88.8** (max 258) vs NORMAL mean **7.66** (~11× separation),
   and LUNA borrow activity is already elevated (54–84/window) in the pre-cascade
   windows *before* `red_deadline`. This is the leading, discriminating signal that
   is genuinely present in the fixtures — and it maps to the 2R.1-deferred
   `utilization` / `borrow_rate` features (and to the 3R.3 B0 baseline).

### Revised recommendation

Un-defer **utilization / borrow-activity** (Aave lending stress), NOT
price/volatility. It is computable from schema-0.1 events (borrow/supply counts
and amounts per window), is ~11× separated crisis-vs-calm, and is elevated
pre-cascade. Open question this raises: if a simple borrow/utilization threshold
(3R.3 baseline B0) already leads by 10 min, the MPS graph model must be shown to
*add* value (3R.3 comparison) — otherwise the simpler detector wins.

## B0 baseline result (2026-08-06) — Success Signal IS achievable

Built the B0 baseline (`engine/baseline.py`, `borrow_activity` = windowed borrow
count) and evaluated it against ground truth. With the RED threshold set at the
**calm control's maximum** windowed borrow activity (FP=0 by construction):

| Threshold | FP (normal) | LUNA lead | FTX lead |
|---|---:|---:|---:|
| normal-max (16 borrow/window) | **0.0%** | **~1748 min (~29 h)** | ~2856 min (~47 h) |
| normal-p95 (11) | 5.3% | ~1793 min | ~2856 min |

**The Success Signal (RED ≥ 10 min early, FP < 5%) is met — easily — by a trivial
borrow-rate detector.** Encoded as a regression test
(`tests/integration/test_baseline_success_signal.py`).

**Honest caveat:** the ~29 h lead means B0 fires from essentially the start of the
crisis fixture — it detects the *elevated-borrow regime* for the whole window, not
the precise cascade moment. It clears the AC, but (a) it is closer to "this is a
stressed period" than "a cascade is imminent", and (b) FP confidence rests on a
single calm control fixture. Still, it is a genuine working detector.

## Strategic implication (decision needed)

B0 (≈30 LOC, no graph, no tensor) already meets the Success Signal with FP=0%.
The MPS graph/entropy model (Epics 2–3) has **not** been shown to beat it — and on
these fixtures its structural signal was *inverted* (§2). Per `research/
literature_review.md` L3 and `research/baseline_detector.md`, MPS must now justify
its complexity or be dropped for v1 (YAGNI). Options: (a) ship B0 as the v1
detector; (b) invest in making MPS add value (utilization node feature + retest,
compare to B0). This is a product/architecture decision, not just a coding task.

## Status

Story 4.1 → Success Signal **achievable via B0 baseline** (working detector +
regression test). MPS-based calibration still **open** (must beat B0 to earn its
place). 4.2/4.3/4.4 unchanged (depend on the chosen detector). 4.2 / 4.3 / 4.4
depend on a discriminating detector and are **not** started (would be building on
sand). The de-risk spike did its job: it prevented investing in calibration,
multiprocessing, and the alert stack on top of a non-discriminating model.
